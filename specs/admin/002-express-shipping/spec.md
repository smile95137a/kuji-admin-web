## Clarifications

### Session 2026-03-30

- Q: 列表 API 分頁策略為何？ → A: 所有列表 API 均支援後端分頁（`page` + `size` 參數），前端實作分頁元件，預設每頁 20 筆。
- Q: 出貨管理路由架構為何？是否需要獨立物流追蹤功能？ → A: 整合進現有訂單管理（擴充 `orderRoutes`），不需獨立出貨路由。前端不整合物流追蹤，管理員以訂單編號查詢訂單；店家自行至物流官網追蹤包裹狀態。
- Q: `statusHistory.operator` 欄位格式為何？ → A: 後端回傳物件 `{ id, email, displayName }`，前端時間軸顯示 `displayName`（或 fallback 至 email）。
- Q: 訂單列表 API 中 prizes 欄位格式為何？ → A: 回傳 `prizeCount: number` 精簡整數欄位，前端直接渲染數字，不回傳完整 prizes 陣列。
- Q: 非法狀態轉換時後端回傳格式為何？ → A: HTTP 422 + `{ errorCode: "INVALID_STATUS_TRANSITION", message: "..." }`；前端捕捉 422 並顯示對應友善提示。

  - 篩選列：

    - 排序下拉（建立時間 DESC/ASC）

- **UI 元件**：

  - 玩家資訊區塊（暱稱、Email）
  - 配送資訊區塊：

    - 宅配：收件人姓名、電話、收件地址

## 使用者情境與測試

### 使用者故事 1 — 店家管理員將訂單更新至「準備中」（優先級：P1）

玩家提出出貨申請後，店家管理員在後台確認訂單並開始處理，將狀態從「待出貨」更新為「準備中」。

**此優先級的原因**：出貨流程的第一個手動步驟，影響玩家對處理進度的感知。

**獨立測試**：建立一筆狀態為「待出貨」的測試訂單，以 StoreOwner 角色登入並完成狀態更新。

**驗收情境**：
1. **在** 訂單狀態為「待出貨」，**當** 店家管理員點擊「標記準備中」並確認，**則** 訂單狀態更新為「準備中」，時間戳記記錄在歷程中。
2. **在** 訂單詳情頁，**當** 管理員確認更新狀態，**則** 狀態徽章即時更新，無需重新載入頁面。
3. **在** 訂單狀態已為「已出貨」，**當** 管理員嘗試退回到「準備中」，**則** 系統不允許，操作按鈕不提供降級選項。

---

### 使用者故事 2 — 店家管理員標記訂單「已出貨」並填寫物流資訊（優先級：P1）

訂單準備完成、實際出貨後，店家管理員更新狀態為「已出貨」，玩家可查看出貨進度。

**此優先級的原因**：「已出貨」是玩家最關注的狀態節點。

**獨立測試**：使用狀態為「準備中」的訂單，完成更新至「已出貨」。

**驗收情境**：
1. **在** 訂單狀態為「準備中」，**當** 管理員點擊「標記已出貨」，**則** 狀態更新為「已出貨」。
2. **在** 更新為「已出貨」後，**當** 查看訂單詳情，**則** 狀態歷程顯示「已出貨」記錄，包含操作員帳號與時間戳記。

---

### 使用者故事 3 — 管理員取消「待出貨」訂單（優先級：P1）

因庫存問題或玩家要求，管理員需要在出貨前取消訂單，獎品退回玩家獎品箱。

**此優先級的原因**：取消功能是售後服務的關鍵，確保玩家權益。

**獨立測試**：建立「待出貨」或「準備中」狀態訂單，執行取消流程並確認獎品退回。

**驗收情境**：
1. **在** 訂單狀態為「待出貨」，**當** 管理員點擊「取消訂單」、輸入原因並確認，**則** 訂單狀態變為「已取消」，獎品退回玩家獎品箱。
2. **在** 訂單狀態為「已出貨」，**當** 管理員進入訂單詳情，**則** 「取消訂單」按鈕為 disabled 狀態，tooltip 說明「已出貨訂單無法取消」。
3. **在** 取消 Modal 中取消原因為空，**當** 點擊「確認取消」，**則** 顯示驗證錯誤「請填寫取消原因」，不送出 API。

---

### 使用者故事 4 — Admin 跨店家查看所有訂單（優先級：P2）

Super Admin 需要跨店家審查所有出貨訂單，監控整體出貨狀況。

**此優先級的原因**：Admin 跨店查詢功能，監控用途，優先級低於核心出貨流程。

**驗收情境**：
1. **在** Admin 角色登入，**當** 進入出貨管理列表，**則** 列表包含所有店家的訂單，且顯示「店家名稱」欄位。
2. **在** StoreOwner 角色登入，**當** 進入出貨管理列表，**則** 僅顯示該店家的訂單，且不顯示「店家名稱」欄位（或該欄固定為自家店家）。

---

### 邊界情況

- 無訂單時，列表顯示空狀態「目前沒有出貨訂單」。
- 訂單獎品列表超過 10 件時，表格加入滾動或分頁。
- 已完成訂單：所有狀態操作按鈕均 disabled。
- 網路超時時，操作按鈕恢復可用，顯示錯誤提示。
- StoreOwner 嘗試存取其他店家的訂單 ID，後端應返回 403，前端顯示「無權限存取此訂單」。
- 非法狀態轉換（如從已完成改回準備中）：後端回傳 HTTP 422 + `INVALID_STATUS_TRANSITION`，前端 Toast 顯示「此狀態無法執行該操作」，按鈕恢復可用。
- **物流追蹤範圍外**：前端不提供物流追蹤功能；配送資訊僅顯示收件資料，店家自行至物流官網查詢。

## API 串接規格

### 出貨訂單管理

| 動作 | Method | 端點 | 主要 Request 欄位 | 主要 Response 欄位 | 前端 UI 狀態 |
|------|--------|------|------------------|--------------------|-------------|
| 取得訂單列表 | POST | `/api/admin/orders/list` | `condition:{status, keyword, startDate, endDate}, sortBy, sortOrder, page, size` | `[{id, orderNo, status, playerName, storeName, shippingMethod, prizeCount, createdAt}]` | loading → 表格渲染 |
| 取得訂單詳情 | GET | `/api/admin/orders/{id}` | — | `{id, orderNo, status, store, player, prizes, shippingInfo, statusHistory:[{status, operator:{id,email,displayName}, timestamp}]}` | loading spinner → 詳情渲染 |
| 更新訂單狀態 | PUT | `/api/admin/orders/{id}/status` | `status: "PREPARING"\|"SHIPPED"\|"COMPLETED"` | `{id, status, updatedAt}` | 按鈕 loading → 狀態更新 |
| 取消訂單 | POST | `/api/admin/orders/{id}/cancel` | `reason: "..."` | `{id, status: "CANCELLED"}` | Modal loading → 關閉 Modal → 狀態更新 |

## 功能需求（前端 UI）

### 介面需求

- **FR-UI-001**：訂單狀態徽章顏色：待出貨（黃）、準備中（藍）、已出貨（紫）、已完成（綠）、已取消（灰）。
- **FR-UI-002**：配送方式以 icon + 文字呈現：超商取貨（🏪 超商取貨）、宅配（🚚 宅配到府）。
- **FR-UI-003**：狀態更新按鈕依當前狀態顯示下一步操作：
  - 待出貨 → 顯示「開始準備」按鈕
  - 準備中 → 顯示「標記已出貨」按鈕
  - 已出貨 → 顯示「確認完成」按鈕
  - 已完成／已取消 → 無操作按鈕
- **FR-UI-004**：狀態歷程以垂直時間軸呈現，最新在上，顯示狀態名稱、操作員顯示名稱（`operator.displayName`，fallback 至 `operator.email`）、時間。
- **FR-UI-005**：訂單詳情頁的配送資訊依 `shippingMethod` 動態渲染不同欄位。
- **FR-UI-006**：列表頁「取消訂單」按鈕僅在狀態為「待出貨」或「準備中」時顯示，其他狀態隱藏或 disabled。
- **FR-UI-007**：ROLE_ADMIN 可見「店家名稱」欄位；ROLE_STORE_OWNER 該欄位隱藏。
- **FR-UI-008**：日期範圍篩選預設為空（顯示全部），使用者手動選擇後才篩選。

### 狀態管理

- **SM-001**：列表初始載入顯示 skeleton loading。
- **SM-002**：API 錯誤時顯示 Toast 錯誤，並說明失敗原因（如「狀態更新失敗，請重試」）。若後端回傳 HTTP 422 + `errorCode: "INVALID_STATUS_TRANSITION"`，Toast 顯示「此狀態無法執行該操作」。
- **SM-003**：狀態更新成功後顯示 Toast「訂單狀態已更新」，並即時更新列表列的狀態徽章。
- **SM-004**：取消訂單成功後，Modal 關閉，列表重新載入（因狀態已變更）。
- **SM-005**：篩選條件變更後自動觸發列表重新查詢（debounce 關鍵字搜尋 300ms）。

## API 驗證清單

- **AV-001** ✅：`POST /api/admin/orders/list` 支援 `status`、`keyword`、`startDate`、`endDate` 篩選 — 符合前端篩選需求。
- **AV-002** ✅：後端依 ROLE_STORE_OWNER 自動過濾店家資料 — 前端無需額外處理跨店權限。
- **AV-003** ✅：`statusHistory.operator` 欄位 — 後端回傳 `{ id, email, displayName }` 物件；前端時間軸顯示 `displayName`（fallback 至 `email`）。
- **AV-004** ✅：訂單列表 Response 中的 prizes 欄位 — 後端回傳 `prizeCount: number`（精簡整數），前端直接渲染，無需 `prizes.length` 計算。
- **AV-005** ✅：`PUT /api/admin/orders/{id}/status` 非法狀態轉換 — 後端回傳 HTTP 422 + `{ errorCode: "INVALID_STATUS_TRANSITION", message: "..." }`；前端捕捉 422 並顯示 Toast 提示「此狀態無法執行該操作」。
- **AV-006** ⚠️：取消訂單後獎品退回機制 — 後端 spec 說明取消後「items return to prize box」，但 API Response 未包含確認資訊；前端無法驗證退回結果，需依賴後端保證。
- **AV-007** ✅：分頁策略已確認 — `POST /api/admin/orders/list` 支援後端分頁（`page`、`size` 參數），前端實作分頁元件，預設每頁 20 筆。
- **AV-008** ✅：配送資訊（超商 vs 宅配）在 `GET /api/admin/orders/{id}` 的 `shippingInfo` 中回傳 — 前端可依 `method` 欄位動態渲染不同 UI。

凡例：✅ 已確認一致 | ⚠️ 需要確認 | ❌ 發現缺口或不一致

## 成功標準

### 可量化的成果

- **SC-001**：管理員可在 2 次點擊內（列表頁點擊按鈕 → 確認）完成訂單狀態更新。
- **SC-002**：訂單列表在 50 筆資料以內，載入時間不超過 2 秒。
- **SC-003**：狀態更新操作回應時間（API + UI 更新）不超過 3 秒。
- **SC-004**：取消訂單流程（含原因輸入 + 確認）最多 3 個步驟完成。
- **SC-005**：日期篩選、狀態篩選、關鍵字搜尋三種條件可同時組合使用。
- **SC-006**：ROLE_STORE_OWNER 登入後，列表頁僅顯示自家店家訂單（無跨店資料洩漏）。
